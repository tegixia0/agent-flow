再动手：agent-flow

我自己搭的一套分阶段、人在回路的 AI 开发流程。流程只写一份、和工具无关，再用一个零依赖的 CLI 装进 Trae、Cursor、Claude Code、CodeAgent，或者任何会读 AGENTS.md 的工具。它的前身是只支持 Trae 和 Cursor、靠手工复制模板的 agent-workflow-kit v1.1。这一页讲我为什么做它、现在的结构、一个小例子的真实运行过程，还有我的一些体会。

01为什么做这个

用 AI 写代码久了，我碰到的问题大多不是“它不会写”，而是“它写得太快、改得太多”。

✏️直接改代码

需求一贴，Agent 马上开始改文件。我还没想清楚要什么，代码已经变了。

🎯范围不受控

“顺手”改了不相关的文件、加了没要求的功能。在已有项目里，这种越界最难发现。

🔁返工

方向错了只能在聊天里来回纠正，改完再改。结论散在对话里，回头也找不到。

🪙token 浪费

一条长对话从头聊到尾，上下文越来越大，每一轮都在为前面的聊天记录付费。

之前我整理过一份《AI 辅助编程提效指南》，讲规则、Skills、MCP 和省 token 的技巧，内容偏“知识”。这次想往前走一步：把这些知识落到一个真正能跑的工作流里，放到实际项目上试，看看哪些有用、哪些只是看起来有用。v1 先在 Trae 和 Cursor 上跑通；v2 想解决另一件事：换工具、换技术栈时，流程本身不用重写。

02它是什么

一句话：

分阶段、人在回路的 AI 开发流程，一份源码装进多种 AI 工具 需求 → 分析 →（影响定位）→ 设计 → 草图 → 计划与实现 → 评审。每个阶段产出一个交接文件，你回复「通过」它才往下走。
Spec-driven development：先写规格，再写代码 Human-in-the-loop：每个阶段之间都要人确认 Agent Skills（SKILL.md） core × packs × adapters 新建 + 存量两种模式 零依赖 CLI

🧩模块化

每个阶段是一个独立 Skill，可以只调用其中一个，比如只用 flow-review 做 CR。

📄不依赖聊天记录

下一阶段只读 docs/flow/0N-*.md 交接文件，所以每个阶段都可以在新对话里继续。

🔍可审计

每个阶段的产物都进 git，可以 diff、可以回滚，事后也能看清每个决定是怎么做出来的。

从 agent-workflow-kit 到 agent-flow

agent-workflow-kit v1.1agent-flow v2.x

🧠core/

流程本身：7 个 flow-* 技能、交接格式与范围护栏规则、6 个阶段代理、项目 AGENTS.md 模板。core/manifest.yaml 描述每个阶段对应的技能、代理、交接文件和适用模式。不含任何工具路径或技术栈细节。

📦packs/

技术栈扩展包：额外规则、技能、各阶段的补充（hook）、验证命令、AGENTS.md 片段，以及何时自动启用（detect）。

🔌adapters/

每个工具一个 adapter.mjs：提供 token 文案，render(model) 返回要写的文件，决定文件放哪、frontmatter 怎么写。

⌨️bin/agent-flow

零依赖 CLI（Node ≥ 18）：安装、自动检测 pack、按指纹安全升级、卸载、生成 pack、构建 dist/。Windows 用 bin\agent-flow.cmd。

几个关键概念

概念位置说明

05核心设计

流程本身只有几个想法，但每个都对应一个我实际踩过的坑。

📑交接文件 + status

每个阶段写一个 docs/flow/0N-*.md，开头是 YAML frontmatter。status 取 draft / approved / done / changes-requested。编排器读取这些文件，找到第一个还没 approved 的阶段继续；上一阶段还是 draft 时不会开始下一阶段。CLI 从不生成或覆盖这些流程产物，只写 docs/flow/README.md。

stage: 01b-impact status: approved # pending 为空 且 approved 非空 mode: brownfield approved: [1, 2, 3, 6, 7] rejected: [4, 5] pending: [] allowed_files: [src/todoTree.ts, package.json, …]

✅逐点审批

存量模式下，01b 把需求拆成改动点 P-n，每个点给出可点击的位置、逐字摘录的当前代码、diff 预览、风险 🟢🟡🔴。你一个个决定：

你说效果
通过 1,3 · 通过 1-3 · 全部通过批准这些点
驳回 2：理由驳回，理由会记录下来
修改 2：意见重写该点预览，有联动的点一起更新
按清单以文件里勾选的 [x] 为准

只有所有点都有决定、并且至少通过 1 个时，才进入实现。部分批准也可以。

🛡️范围护栏 allowed_files

实现阶段只能实现已批准的点，只能改 allowed_files（= 已批准点涉及的文件）。需要改其他文件、新建文件或补测试时，先在 01b 里追加「新发现点」，然后回复 ⛔ 需要超出已批准的范围… 并暂停。完成后用 git diff --name-only ⊆ allowed_files 做范围核对，评审阶段再核一次。

这条护栏写在三处：flow-implement 技能、flow-scope-guard 规则、始终加载的 AGENTS.md，层层兜底。

👥子代理分工

编排器（flow-orchestrator）不做具体工作，只负责判断阶段、委派、停下等确认。每个阶段交给一个专职子代理：

flow-analyst · 分析flow-locator · 影响定位flow-designer · 设计 flow-sketcher · 草图flow-implementer · 实现flow-reviewer · 评审（readonly）

中性代理定义只写一份，由 adapter 渲染成各工具的格式：Cursor 的 reviewer 是 readonly: true，Claude Code / CodeAgent 用 skills: 预加载对应技能，Trae 由内置 Agent 调用。

🔀一份源码，按工具渲染

v1 里同一份技能要放在 .trae/skills/ 和 .cursor/skills/，靠 sync-skills.sh 同步。v2 改成只维护 core/ 和 packs/ 里的中性格式，安装时由 adapter 渲染：规则在 Cursor 里是 .mdc，在 Claude Code 里只用 paths；只有某个工具需要的文字用 <!--@only cursor--> 这样的条件块包起来（比如 Cursor 的只读 reviewer 不能写文件，就改成“把 05-review.md 的内容返回给主代理”）。Skill 按需加载、规则全程占上下文，所以详细步骤都写进 Skill，规则只写入口和护栏。

🟦Trae

规则用 description / globs / alwaysApply，子代理的 tools 含 Skill。依据 docs.trae.ai 的 Rules / Skills / Subagents 页面（2026-10 核对）。需要在设置里打开 AGENTS.md 和 Subagents 开关，且只有内置 Agent 能调用子代理。

⬛Cursor

规则是 .mdc；子代理带 model: inherit 和 readonly，技能用 /name 调用。注意 Cursor 也会读 .claude/skills/，同时装 cursor 和 claude 时可能看到两份同名技能，内容只在路径提示上不同。

🟧Claude Code

依据 code.claude.com 的 memory、skills、sub-agents 文档（2026-10 核对）。Claude Code 只在没有 CLAUDE.md 时才读 AGENTS.md，所以生成的 CLAUDE.md 第一行是 @AGENTS.md；已有 CLAUDE.md 时不覆盖，请自己加这一行。规则只用 paths，没有 globs 的规则不写 frontmatter、始终加载。

📄generic

给只认 AGENTS.md 的工具（Codex、Copilot coding agent、Jules、Zed、Windsurf 等）：规则内联到 AGENTS.md 末尾的「流程规则（agent-flow）」一节，技能和代理放在 docs/agent-flow/ 下按路径引用。

⚠️ CodeAgent（--tool codeagent，别名 cac）：格式为假定，未经核对

CodeAgent 没有公开文档。.cac/ 的目录布局来自我拿到的说明，frontmatter 全部照搬 Claude Code 的格式，属于 assumed, unverified。实现上复用了 claude-code adapter 的 renderClaudeLayout(model, '.cac')，只替换目录、token 和入口说明。

因为没核对过，它不在 --tool all 里，需要时显式写 --tool all,cac。只装 codeagent 时不写根目录 AGENTS.md（.cac/AGENTS.md 已是完整说明；CodeAgent 是否同时读根目录未知）；和其他工具同装时两份都写，由 lock 分别跟踪。

agent-flow 绝不创建或修改 .cac/settings.json、.cac/AGENTS.local.md、output-styles/、hooks/、agent-memory/、agent-memory-local/（adapter 里有断言，测试也会校验）。拿到官方文档后需要逐项核对。

07技术栈 pack

pack 是某个技术栈的“补充说明”。--packs auto（默认）按项目文件自动检测；也可以 --packs none 或 --packs a,b 手动指定。

pack状态自动检测验证命令附带
vscode-extension 1.0.0stablepackage.json 有 engines.vscodenpm run compile · npm test · npx @vscode/vsce package（只打包不发布）规则 vscode-extension、vscode-webview；技能 vscode-release；6 个阶段 hook
web 1.0.0stable依赖里有 next / vite，或存在 next.config.* / vite.config.*npm run lint · npx tsc --noEmit · npm test · npm run build · npx playwright test规则 web-frontend；技能 web-verify-ui；6 个阶段 hook
java-backend 0.1.0skeletonpom.xml、build.gradle、build.gradle.kts 任一./mvnw -q verify · ./gradlew build规则 java-spring；analyze / locate / design / implement / review hook
_template模板——new-pack 复制它并替换 {{PACK_NAME}}

java-backend 是骨架：结构完整、可以安装，但约定内容还没在真实 Spring Boot 项目上跑通，不确定的条目都标了 TODO(未验证)，转 stable 前要逐条确认。build 默认只包含 stable 的 pack。

加一个新 pack

1生成骨架

new-pack rust-cli，放仓库外用 --packs-dir。

2写 pack.yaml

detect、verify、rules、skills、hooks、agentsMd；未验证的写 TODO(未验证)，保持 status: skeleton。

3验证

list-packs --project 目录 看 ✔ 是否命中，build --packs rust-cli 看渲染结果，npm test 自动检查 frontmatter。

4提交

pack 改动单独提交，例如 feat(pack): add rust-cli (skeleton)，并更新 CHANGELOG。

第三方 pack：--packs-dir ./my-packs（可重复）或环境变量 AGENT_FLOW_PACKS_PATH。

08CLI

零依赖，只需要 Node.js ≥ 18。macOS / Linux 用 bin/agent-flow，Windows 用 bin\agent-flow.cmd（cmd 和 PowerShell 都能调用），也可以直接 node bin/agent-flow.mjs。

命令作用
init <目录> --tool …安装。--tool 必填（不会默认装全部）。可选 --packs auto|none|a,b、--mode auto|greenfield|brownfield。先打印计划再问 y/N；--dry-run 只看计划，--yes / -y 跳过确认。记录 .agent-flow/lock.json
upgrade [目录]按 lock 里记录的工具、packs、模式重新渲染（不接受 --tool）。按文件指纹判断：只覆盖你没改过的文件，改过的写成 <文件>.agent-flow-new；--force 才强制覆盖
uninstall <目录> [--tool x,y]只删除 lock 里记录、且未被修改的文件，以及 agent-flow 新建的空目录；改过的文件列出并保留。按工具卸载时保留其他工具还需要的共享文件。不加 --tool 卸载全部
list-packs [--project 目录]列出 pack；带 --project 时用 ✔ 标出检测命中的 pack
new-pack <名称>从 packs/_template 生成新 pack（--packs-dir 指定位置）
build [--packs stable|all|none|a,b]为每个工具渲染 dist/<tool>/，方便查看或手动复制

09安全措施

这个工具会往别人的项目里写文件，所以我给它定的原则是：宁可报错、宁可多问一句，也不要悄悄写错或覆盖。

🚫从不覆盖你的文件

init 只新建文件；已存在且不是 agent-flow 生成的文件一律跳过。已有 AGENTS.md → 写 AGENTS.flow.md，需要你手动合并；已有 CLAUDE.md → 保留；已有非 agent-flow 生成的 .cac/AGENTS.md → 写 .cac/AGENTS.flow.md。

🔏按指纹升级

每个写入的文件在 .agent-flow/lock.json 里记一个指纹（sha256 前 16 位，按 LF 计算）。upgrade 时指纹一致 → 覆盖；不一致（你改过）→ 写 <文件>.agent-flow-new 让你自己合并。uninstall 同理，只删没改过的。

🧾严格参数 + 建议

未知命令和选项、单横线长选项、缺值、开关带值、多余的位置参数都会报错（退出码 2），并给出最接近的写法；--tool / --mode / --packs 的值拼错也会提示候选。

✋先看计划再确认

init / upgrade / uninstall 先打印计划：目标目录、工具、模式、packs、新建/跳过/冲突数量、AGENTS.flow.md 提示等，再在终端问 y/N。非交互环境（CI、脚本、管道）没有 --yes 会直接拒绝执行。确认时取消返回 1。

🎯--tool 必填

init 必须明确写出装哪些工具，不再默认 all；upgrade 使用 lock 里记录的工具。

🗂️受保护的 .cac/ 文件

.cac/settings.json、AGENTS.local.md、output-styles/、hooks/、agent-memory*/ 永远不碰；卸载时也不会删项目根、docs/、docs/flow/。

10Windows 支持

↵换行

⌨️入口

13Token 成本与省 token 做法

先说实话：分阶段一定比“一句话让 AI 直接改”多几轮对话、多几份文档。我没有做精确的 token 计量，示例里也没有记录用量数据，所以这里只讲成本从哪来、我怎么压。

➕额外成本在哪

  • 阶段多：每个阶段至少一轮对话，加上确认和修改。
  • 交接文件要被下一阶段重新读取。
  • 01b 要逐字摘录代码、写 diff 预览，比直接改代码多产出不少文字。
  • 实现中途 ⛔ 暂停再继续，会多一轮往返。
  • 启用 pack 后，相关阶段技能末尾会多一段「技术栈补充」。

➖换来的是

  • 方向在写代码前就被纠正（示例里 P-4、P-5 在 01b 就被驳回，没有写了再删）。
  • 不用在一个越来越长的对话里反复解释上下文。
  • 结论都在文件里，换个人、换个工具也能接着做。

用到的省 token 做法

做法具体怎么做
每个阶段新开对话第一句写「继续流程」，编排器读取 docs/flow/ 判断进度。下一阶段只读交接文件，不依赖聊天记录。
Skill 按需加载编排器“只读取当前阶段对应的那个技能”；规则全量注入、Skill 按需注入，所以详细步骤都放 Skill。
规则限定作用范围交接格式规则用 globs: docs/flow/**，只在读写交接文件时生效（Claude Code / CodeAgent 里渲染成 paths）。
技术栈内容按需装VS Code、Web、Java 的要点放在 pack 里，只有检测命中或指定的 pack 才会进入技能。
交接文件精简只写结论；不粘贴完整日志；单个 .md 尽量 ≤ 200 行；01b 代码摘录 ≤ 15 行。
子代理隔离阶段工作委派给子代理，主对话只看到摘要和确认提示。
AGENTS.md 写短只写技术栈、目录、命令、约定（指南建议约 200 行以内），作为各工具共用的事实来源。

指南里还提到几条我在这个项目之外也在用的：忽略 dist/、out/、node_modules/ 等噪声目录；能用 CLI 就不用 MCP；不用的 MCP 关掉；换任务直接新开对话，因为 prompt caching 只对不变的前缀有效。

15我的收获与下一步探索

跑完两轮小例子、又把它重构成 v2 之后的一些想法。样本很小，下面更多是体会而不是结论。

“先列改动点”比“写得好”更重要

在已有代码上，我最在意的是 AI 会不会乱改。01b 把每个点落到文件和行号、配上 diff 预览之后，我在写代码前就能判断“这个要、这个不要”。示例里状态栏和持久化两个点就是在这一步被我拿掉的。

⛔ 暂停是设计目标，不是故障

实现中途发现要改白名单外的文件时，Agent 停下来问我，而不是默默改掉。这次的理由（为了可单测，抽出纯函数）是合理的，我批准了；但关键是这个决定由我来做，并且有记录可查。

人在回路有代价

每一步都要我看、要我回复，节奏明显变慢。小改动走完整流程不划算，所以留了「连续模式」和单独调用某个阶段的入口。什么规模的需求值得走流程，我还没有清晰的标准。

验证还没闭环

单测 5/5 通过，但集成测试在示例环境里没有运行，几项 UI 验证也标注为“需手动”。评审能核对范围，却没法替代真正跑起来看一眼。

把“工具差异”从流程里拿出去

v1 时两份目录靠同步脚本维护，加第三个工具就会失控。v2 把差异收进 adapter 之后，加 Claude Code、CodeAgent 基本只是写一个渲染器，流程文字一行不用动。同样，技术栈的内容进了 pack，core 里只剩通用表述。

安装工具本身也要“人在回路”

2.2.0 修的问题很典型：少打两个横线，CLI 不报错，却装上了我没要的工具。流程里我要求 AI 先给计划再动手，CLI 现在也一样：先打印计划、问 y/N、参数不对就停下给建议。

没核对过的就明说

CodeAgent 的格式我没法核对，所以文档、代码、CHANGELOG 里都标了 assumed, unverified，也不放进 --tool all；java-backend 同样标着 TODO(未验证)。宁可少支持一点，也不要让人误以为它已经验证过。

下一步想试的

🔎核对 CodeAgent、补齐 java-backend

拿到 CodeAgent 官方文档后逐项核对 .cac/ 的格式；找一个真实的 Spring Boot 项目跑通 java-backend，把 TODO(未验证) 一条条消掉，再转 stable。

⚡并行子代理

现在是一个阶段一个子代理、串行推进。想试试在 01b 定位或评审时把不同模块交给多个子代理并行处理，看看速度和质量会怎么变，冲突怎么合并。

🎭Playwright CLI 做验证

web pack 已经把 npx playwright test 列为验证命令。想进一步把 Playwright CLI + Skill 接进 04/05，让“需手动验证”的项变成可自动执行的检查。

🚦CI 门禁

范围核对现在靠 Agent 自己跑 git diff。如果把“改动文件 ⊆ allowed_files”和“交接文件 status 正确”放进 CI，就不必只相信 Agent 的自查。
