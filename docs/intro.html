01为什么做这个

用 AI 写代码久了，我碰到的问题大多不是“它不会写”，而是“它写得太快、改得太多”。

✏️直接改代码

需求一贴，Agent 马上开始改文件。我还没想清楚要什么，代码已经变了。

🎯范围不受控

“顺手”改了不相关的文件、加了没要求的功能。在已有项目里，这种越界最难发现。

🔁返工

方向错了只能在聊天里来回纠正，改完再改。结论散在对话里，回头也找不到。

🪙token 浪费

一条长对话从头聊到尾，上下文越来越大，每一轮都在为前面的聊天记录付费。

之前我整理过一份《AI 辅助编程提效指南》，讲规则、Skills、MCP、省 token 的技巧，偏“知识”。这次想往前走一步：把这些知识落到一个能真正跑起来的工作流里，在实际项目上试一下，看看哪些有用、哪些只是看起来有用。

02它是什么

一句话：

分阶段、人在回路的 AI 开发工作流模板 需求 → 分析 → 设计 → 草图 → 计划与实现 → 评审。每个阶段产出一个交接文件，你回复「通过」它才往下走。
Spec-driven development：先写规格，再写代码 Human-in-the-loop：每个阶段之间都要人确认 Agent Skills（SKILL.md） Trae / Cursor 通用 新建 + 存量两种模式

🧩模块化

每个阶段是一个独立 Skill，可以只调用其中一个，比如只用 flow-review 做 CR。

📄不依赖聊天记录

下一阶段只读 docs/flow/0N-*.md 交接文件，所以每个阶段都可以在新对话里继续。

🔍可审计

每个阶段的产物都进 git，可以 diff，可以回滚，事后也能看清每个决定是怎么做出来的。

04核心设计

整个套件只有几个想法，但每个都对应一个我实际踩过的坑。

📑交接文件 + status

每个阶段写一个 docs/flow/0N-*.md，开头是 YAML frontmatter。status 取 draft / approved / done / changes-requested。编排器读取这些文件，找到第一个还没 approved 的阶段继续执行；上一阶段还是 draft 时不会开始下一阶段。

stage: 01b-impact status: approved # pending 为空 且 approved 非空 mode: brownfield approved: [1, 2, 3, 6, 7] rejected: [4, 5] pending: [] allowed_files: [src/todoTree.ts, package.json, …]

✅逐点审批

存量模式下，01b 把需求拆成改动点 P-n，每个点给出可点击的位置、逐字摘录的当前代码、diff 预览、风险 🟢🟡🔴。你一个个决定：

你说效果
通过 1,3 · 通过 1-3 · 全部通过批准这些点
驳回 2：理由驳回，理由会记录下来
修改 2：意见重写该点预览，有联动的点一起更新
按清单以文件里勾选的 [x] 为准

只有所有点都有决定、并且至少通过 1 个时，才进入实现。部分批准也可以。

🛡️范围护栏 allowed_files

实现阶段只能实现已批准的点，只能改 allowed_files（= 已批准点涉及的文件）。需要改其他文件、新建文件或补测试时，先在 01b 里追加「新发现点」，然后回复 ⛔ 需要超出已批准的范围… 并暂停。完成后用 git diff --name-only ⊆ allowed_files 做范围核对，评审阶段再核一次。

这条护栏写在三处：flow-implement 技能、flow-scope-guard 规则、始终加载的 AGENTS.md，层层兜底。

👥子代理分工

编排器（flow-orchestrator）不做具体工作，只负责判断阶段、委派、停下等确认。每个阶段交给一个专职子代理：

flow-analyst · 分析flow-locator · 影响定位flow-designer · 设计 flow-sketcher · 草图flow-implementer · 实现flow-reviewer · 评审（readonly）

Cursor 放在 .cursor/agents/，reviewer 设成 readonly: true；Trae 放在 .trae/agents/，由内置 Agent 调用。

🔀基于 Skill，所以能跨工具

7 个 flow-* 技能都是标准的 SKILL.md（遵循 agentskills.io 格式），同一份内容放在 .trae/skills/ 和 .cursor/skills/，用 sync-skills.sh 保持同步。规则文件两边 frontmatter 字段基本一致（description / globs / alwaysApply），AGENTS.md 作为两边共用的唯一事实来源。Skill 按需加载，规则全程占上下文，所以详细步骤都写进 Skill，规则只写入口和护栏。

05实例演示：给 TODO Lens 加「按标签筛选」

TODO Lens 是一个 VS Code 扩展：在侧边栏列出 TODO / FIXME，点击跳转，状态栏显示计数。第 1 轮用新建模式从零做出 v0.1；第 2 轮在它上面用存量模式加功能。下面是第 2 轮。

需求原文（00）：给 TODO Lens 加按标签筛选。视图标题栏加一个筛选按钮，可以选“全部 / TODO / FIXME”（跟着配置的关键字走）；视图标题旁边显示当前筛选；状态栏也显示筛选后的数量；筛选在重启 VS Code 后保留。

阶段 1 把它拆成 5 条验收标准：AC-1 筛选按钮 + QuickPick；AC-2 列表按标签过滤；AC-3 标题旁显示“筛选：X”；AC-4 状态栏显示“筛选后/总数”；AC-5 重启后保留筛选。

🧐评审发现的问题

R-1 🟡 筛选结果为空时，视图会显示“当前工作区没有找到 TODO / FIXME 注释”，会误导用户。这个位置在 01b 里被列为“未触及”，所以本次没改，符合范围；建议下一轮作为新改动点处理。
R-2 🔵 关键字配置里删掉当前筛选的标签时，筛选不会自动清除，列表会变空。

评审给出的下一步是「回到 1b：修复 R-1」——问题会作为新改动点重新定位、重新审批，不会直接改代码。

说明：这是示例环境中的运行，示例项目没有 git，01b 的 baseline 写的是 v0.1.0；在真实项目里应该是 git rev-parse --short HEAD。部分验证（标题栏图标、视图描述）标注为需要手动确认。

06如何使用

安装

./agent-workflow-kit/install.sh /path/to/your-project               # Trae 和 Cursor 都装（默认）
./agent-workflow-kit/install.sh /path/to/your-project --trae        # 只装 Trae（--cursor 只装 Cursor）
./agent-workflow-kit/install.sh /path/to/existing-project --brownfield   # 已有项目：默认存量模式
./agent-workflow-kit/install.sh /path/to/project --upgrade          # 从 v1.0 升级：覆盖 flow-* 技能、规则和智能体

1不覆盖已有文件

默认只新增文件。项目里已有 AGENTS.md 时会生成 AGENTS.flow.md，需要手动合并「开发流程」一节。

2填写项目信息

把 AGENTS.md 的「项目信息」（技术栈、命令、约定）填好，这是性价比最高的上下文。

3先提交一次

存量模式建议在 git 仓库里用、开始前先提交：01b 记录 baseline，04 和 05 用 git diff 做范围核对。

Trae 必做设置

  1. 设置 > 规则：打开「将 AGENTS.md 包含在上下文中」。
  2. 设置 > Beta > Subagents：确认「启用 Subagents 目录」已打开（通常默认开启）。
  3. 对话时选择内置的 「Agent」 智能体——只有内置 Agent 能调用 .trae/agents/ 里的子智能体。
  4. （可选）想直接 @ 某个阶段的智能体：创建智能体，把 .trae/agents/flow-*.md 正文粘贴为提示词，勾选对应工具并打开「可被其他智能体调用」。

Cursor 不需要额外设置，在 Customize > Skills 中能看到 7 个 flow-* 技能。

07Token 成本与省 token 做法

先说实话：分阶段一定比“一句话让 AI 直接改”多几轮对话、多几份文档。我没有做精确的 token 计量，示例里也没有记录用量数据，所以这里只讲成本从哪来、我怎么压。

➕额外成本在哪

  • 阶段多：每个阶段至少一轮对话，加上确认和修改。
  • 交接文件要被下一阶段重新读取。
  • 01b 要逐字摘录代码、写 diff 预览，比直接改代码多产出不少文字。
  • 实现中途 ⛔ 暂停再继续，会多一轮往返。

➖换来的是

  • 方向在写代码前就被纠正（示例里 P-4、P-5 在 01b 就被驳回，没有写了再删）。
  • 不用在一个越来越长的对话里反复解释上下文。
  • 结论都在文件里，换个人、换个工具也能接着做。

套件里用到的省 token 做法

做法具体怎么做
每个阶段新开对话第一句写「继续流程」，编排器读取 docs/flow/ 判断进度。下一阶段只读交接文件，不依赖聊天记录。
Skill 按需加载编排器“只读取当前阶段对应的那个技能”；规则全量注入、Skill 按需注入，所以详细步骤都放 Skill。
规则限定作用范围交接格式规则用 globs: docs/flow/**，只在读写交接文件时生效；入口规则和护栏规则是“智能生效”。
交接文件精简只写结论；不粘贴完整日志；单个 .md 尽量 ≤ 200 行；01b 代码摘录 ≤ 15 行。
子代理隔离阶段工作委派给子代理，主对话只看到摘要和确认提示。
AGENTS.md 写短只写技术栈、目录、命令、约定（指南建议约 200 行以内），作为两款 IDE 共用的事实来源。

指南里还提到几条我在这个套件之外也在用的：忽略 dist/、out/、node_modules/ 等噪声目录；能用 CLI 就不用 MCP；不用的 MCP 关掉；换任务直接新开对话，因为 prompt caching 只对不变的前缀有效。

08我的收获与下一步探索

跑完两轮小例子后的一些想法。样本很小，下面更多是体会而不是结论。

“先列改动点”比“写得好”更重要

在已有代码上，我最在意的是 AI 会不会乱改。01b 把每个点落到文件和行号、配上 diff 预览之后，我在写代码前就能判断“这个要、这个不要”。示例里状态栏和持久化两个点就是在这一步被我拿掉的。

⛔ 暂停是设计目标，不是故障

实现中途发现要改白名单外的文件时，Agent 停下来问我，而不是默默改掉。这次的理由（为了可单测，抽出纯函数）是合理的，我批准了；但关键是这个决定由我来做，并且有记录可查。

人在回路有代价

每一步都要我看、要我回复，节奏明显变慢。小改动走完整流程不划算，所以套件里留了「连续模式」和单独调用某个阶段的入口。什么规模的需求值得走流程，我还没有清晰的标准。

验证还没闭环

单测 5/5 通过，但集成测试在示例环境里没有运行，几项 UI 验证也标注为“需手动”。评审能核对范围，却没法替代真正跑起来看一眼。这是下一步最想补的地方。

写成 Skill，跨工具基本可行

同一套 SKILL.md 在 Trae 和 Cursor 里都能用，差别主要在规则文件后缀、子代理字段和 Trae 的几个开关。维护两份目录靠一个同步脚本，目前还能接受。

下一步想试的

⚡并行子代理

现在是一个阶段一个子代理、串行推进。想试试在 01b 定位或评审时把不同模块交给多个子代理并行处理，看看速度和质量会怎么变，冲突怎么合并。

🎭Playwright CLI 做验证

指南里提到 Playwright CLI + Skill 比 Playwright MCP 更省 token，快照写到文件而不是塞进上下文。想把它接进 04/05，让“需手动验证”的项变成可自动执行的检查。

🎨Figma MCP

03 草图阶段现在是 ASCII 线框图加单文件 HTML 原型。想探索从设计稿读取信息来驱动这一阶段，前提是先弄清楚它对上下文的占用。

🚦CI 门禁

范围核对现在靠 Agent 自己跑 git diff。如果把“改动文件 ⊆ allowed_files”和“交接文件 status 正确”放进 CI，就不必只相信 Agent 的自查。
