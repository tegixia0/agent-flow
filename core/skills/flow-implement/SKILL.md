# 阶段 4：计划与实现

本阶段内部有**两个子步骤**，中间有一个人工确认点。

## 输入
- **新建模式**：`docs/flow/01-analysis.md`、`02-design.md`、`03-sketch.md`（均需 `status: approved`）
- **存量模式（brownfield）**：`docs/flow/01-analysis.md` + `01b-impact.md`（`status: approved`）；如果有 02、03，也一并读取
- `AGENTS.md` 中的构建和测试命令

## 输出
- `docs/flow/04-plan.md`（按 `assets/template.md` 的结构）
- 源码和测试改动

## 4a 写计划（状态：draft）
1. 把 02 中的"模块与文件"拆成 3–10 个任务 `T-1…T-n`。每个任务应能在 15 分钟内完成，并写明：改哪些文件、对应哪些 AC、怎么验证。
2. 排出顺序：先类型和纯逻辑（可以单测）→ 再接入平台（命令、视图、路由）→ 最后补 UI 细节。
3. 写清本次会运行的命令，例如 `npm run compile`、`npm test`。
4. 写入 `04-plan.md`，`status: draft`，按编排器模板停下，**等待"通过"**。

## 4b 实现（状态：approved → done）
1. 按任务顺序实现。每完成一个任务：
   - 运行最小验证（类型检查或相关测试），**只把失败的摘要**记进"实施记录"，不要粘贴完整日志；
   - 在清单中勾选 `[x]`。
2. 偏离计划时（例如发现设计不可行）：停下，在"偏差"小节写明原因和建议，询问用户，不要擅自大改设计。
3. 全部完成后，运行完整的测试和构建，把结果写进"实施记录"，把 `status` 改为 `done`，然后提示用户进入阶段 5 评审。

## 存量模式（brownfield）的范围护栏 —— 必须遵守
1. **只实现 `approved` 中的点**。计划里每个任务都要标明对应的 `P-n`；`rejected` 的点在计划中列为"不做"。
2. **只修改 `allowed_files` 中的文件**，并且尽量只改该点给出的行区间附近。每次编辑前，先核对目标文件是否在白名单里。
3. **遇到新文件或新改动点时立即停下**：如果实现过程中发现必须修改清单之外的文件或区域（包括新建文件、补测试文件、改配置），**不要先改**。按下面步骤处理：
   - 在 `01b-impact.md` 的"新发现点"中追加 `P-n`（`pending`），写明位置、原因、diff 预览和风险，同时更新 frontmatter 的 `pending`；
   - 用下面的模板回复，然后**结束本轮**：
     ```
     ⛔ 需要超出已批准的范围
     新发现点 P-n：<路径#L起-L止> —— <为什么需要>
     预览：<3–8 行 diff>
     请回复「通过 n」或「驳回 n」。驳回时，我会说明替代方案或对 AC 的影响。
     ```
   - 用户回复后，由 flow-locate 的规则更新 01b，然后再继续实现。
4. 实际改动与预览不一致时（例如函数名或位置不同）：如果仍在同一文件、同一意图内，可以继续，但要在摘要的"与预览差异"一栏写明；如果意图改变，按第 3 条停下。
5. 完成后在 `04-plan.md` 中填写 **"按点变更摘要"**（见 `assets/template.md`），每个 P-n 一行，**包括被驳回的点**（写"未修改"）。最后附上范围核对结果：`git diff --name-only <baseline>` 的文件列表 ⊆ `allowed_files`。

## 编码约定（无项目约定时的默认值）
- 开启语言的严格模式或类型检查（例如 TypeScript `strict`），不使用逃逸类型（例如 `any`）；生命周期资源要统一注册、统一释放。
- 技术栈相关约定见本文件末尾的「技术栈补充」。
- 新增依赖之前，先在计划中说明理由。
- 每个 AC 至少对应一个自动化测试，或在计划中写明手动验证步骤。

## 不要做
- 计划还没被确认就写代码。
- 修改 `docs/flow/01–03`；如果有需要改的地方，记在"偏差"里，由用户决定是否"回到 2"。
