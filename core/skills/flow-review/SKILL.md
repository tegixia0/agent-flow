# 阶段 5：评审（只读）

## 输入
- `docs/flow/01–04`（04 需为 `status: done`）；存量模式下还要读取 `01b-impact.md`
- 代码改动：优先使用 `git diff <基线>...HEAD --stat`，再按需查看具体文件的 diff；没有 git 时，读取 04 中列出的文件
- 测试和构建结果：可以重新运行一次测试，只记录汇总

## 输出
- `docs/flow/05-review.md`（按 `assets/template.md` 的结构）
- `status`：没有 🔴 问题时写 `approved`（这是评审结论，仍需人工最终确认）；有 🔴 问题时写 `changes-requested`

## 步骤
1. **AC 核对**：逐条检查 `AC-x`，结论为 ✅ / ⚠️ / ❌，并给出证据（文件:行号、测试名或手动步骤）。
2. **范围核对（存量模式必做）**：
   - `git diff --name-only <baseline>` 列出的文件 ⊆ `01b-impact.md` 中的 `allowed_files`；如有越界，记为 🔴
   - 每个被驳回的点，对应区间都没有被修改；如有修改，记为 🔴
   - 04 的"按点变更摘要"覆盖了所有 P-n，链接指向的是改动后的行号
3. **设计一致性**：实现是否偏离 02 的模块划分和 ADR；偏离是否已记录在 04 的"偏差"里。
4. **代码问题**：按严重级别列出：
   - 🔴 必须修：缺陷、安全问题（XSS、Webview CSP 缺失、命令注入、密钥泄露）、数据丢失
   - 🟡 建议修：性能、错误处理、资源泄漏（例如漏注册 Disposable）、可访问性
   - 🔵 可选：命名、风格、重复代码
5. **测试评估**：哪些 AC 没有自动化测试；测试是否真的断言了行为。
6. **结论与下一步**：通过，或返回阶段 4 修复（列出需修复的问题编号）。

## 规则
- 每个问题都必须有 `文件:行号` 和可执行的修改建议。
- 不要重写代码；最多给出 ≤10 行的修复片段。
- 用户接受评审后，修复工作交回 `flow-implement`，在 04 的"实施记录"中追加修复记录，然后重新评审。
